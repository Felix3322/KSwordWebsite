01 / SCOPE

Source and release boundary

Reviewed on 2026-10-13 against KSwordDEV/KSword@a996d38d91c85a9d99744454880a58b7b223f7f7, committed on 2026-10-13. This update covers main-branch progress since the previous review and retains the implementation and evidence limits of existing features. Uncommitted workspace changes are outside this snapshot. Downloaded packages may not contain every change in this commit.

Check source capabilities and downloadable assets separately.

Use the changelog and GitHub Releases for assets. Deploy the matching application, driver, both API agents, language packs, profiles and plugins. A capability flag, visible button, successful build, driver load and scenario acceptance are different results.

02 / AUTOMATION

MCP and CLI automation

The application now has a generic Qt object bridge connected to a standalone stdio sidecar over a local named pipe. It discovers pages and lazy subpages, reads controls, tables and text, invokes supported native actions and exposes operation receipts. Checkboxes accept an explicit boolean state without toggling again when already set. Custom-painted professional controls still need adapters. Object lifetime, table-model revision and business completion require separate checks; dispatch alone does not prove the result.

“Settings → MCP” provides session start/stop, an auto-start preference, client configuration previews and a bounded operation log. Auto-start is off by default; --mcp enables one application session. The external sidecar and installation guide live in KSwordDEV/MCP. Launching the application on demand requires an explicit policy, and elevated startup needs the user's Windows UAC approval. Installation, discovery, client loading and GUI connectivity are checked separately, without automatically changing other MCP entries or restarting an existing application.

KswordCLI's R3 commands cover process, network, file, registry, service, startup, window and security evidence, with UTF-8 text or JSON and explicit partial, unsupported and unavailable results. MCP can use an explicit CLI path independently of the GUI. Status/help are read-only; arbitrary CLI commands and GUI mutations require confirmed=true, while native command confirmations remain in place.

system ioctl call sends one raw request through the existing ArkDriverClient to the fixed KSword control device. It requires --confirm and caps input and output at 1 MiB each. It keeps the caller's permissions and does not automatically load the driver, elevate or retry. Transport success, response ABI and driver business status are assessed separately.

03 / REPORTS

Complex reports and PEB workspace

The Process Detail Evidence “Structure report” preserves the Domain → Type → Field → Property hierarchy, fixed section summaries and tools, collapsible groups and inline properties or full text. Only visible rows are painted, avoiding a widget per field. Search includes collapsed descendants and complete values; clearing it restores the reading position. Copy-all and export use the same canonical document without truncating it to the current filter or expansion state. Producer-side missing or truncated data stays explicit.

“Process → Process details → PEB” restores the shared parameter/result workspace: parameters scroll independently, execution actions stay fixed, and summaries and read-only guidance appear on first display. Narrow windows stack the panes. Lazy field projections and thread details retain control identity and search/copy/export semantics; the layout change adds no PEB write or sampling permissions.

Saved checks use the actual application in dark/light themes, at roughly 800px width and across search-state changes. The complex-report session covers static catalogs and error states. Successful driver sampling, complete clipboard/file export flows, DPI and all background modes still have unverified cases; separate thread sampling and other old report sources have not all migrated.

04 / WORKBENCHES

Registry and permission workbenches

The registry now has a typed workbench with location tabs, favorites/history, 32/64-bit views, name/type/data searches, full-value editing and a staged-change list. Applying changes checks the read baseline and verifies through the selected channel. Original subtree backups, supported last-commit restoration, key permissions and offline Hive working copies are available. Staging does not write the registry; summaries and partial reads are not complete values.

The permission pages cover accounts/groups, LSA rights assignments, token comparison, access diagnostics, logon-session/process links, identity launches and manual permission snapshots. Accounts use SID identity and processes use PID plus creation time. Direct policy assignments, actual tokens and handle-open results remain distinct. Snapshot comparisons retain JSON value types and collection errors; missing evidence stays unconfirmed and snapshots do not automatically restore permissions.

Account, group and policy changes retain previews, confirmation and readback. UAC, SYSTEM and TrustedInstaller launches have their own permission requirements. Saved read-only/model regressions do not establish acceptance of live account writes, policy changes or elevated launches.

05 / CKS RESEARCH

CKS management and reset-free research

“Miscellaneous → CKS management” has three pages: “Current Microsoft workflow”, “SSDE experimental workflow” and “Reset-free research”, sharing current-system evidence and results. Research records exact component identities, enrollment paths and a verification template, keeping historical samples separate from live queries.

Reset-free first enrollment remains unverified research.

Re-establishing enrollment before startup and a repair installation that preserves applications are separate candidates without a validated successful workflow. Refreshing policy does not turn an existing disabled enrollment into first enablement. License values, policy files or CiTool success do not prove driver trust. Actual policy/signatures, driver loading and persistence across restart and updates still need validation; static research is not a working feature.

06 / MEMORY

Shared memory editor and Intel assembly

The main application's R3/R0/R-1, DDMA, shadow-page, hook-wizard, kernel-disassembly and captured-dump views share one snapshot component. Hex, text, disassembly and comparison use the same bytes, with pending edits, changes between reads and local undo/redo.

The x86/x64 Intel assembler supports multiple lines, local labels, address-aware branches and RIP-relative operands. Numbers default to hexadecimal; use 0d for decimal. Compilation stages bytes; the owning page explicitly applies them with checks before writing and actual readback afterwards. CE Auto Assembler scripts are not supported. A read-only view gains no write capability.

R3/R0 region dumps

The main Memory page and the process-detail region list offer separate R3 and R0 region-dump exports. Output is a raw .bin equal to the region length, distinct from a whole-process dump or minidump. Export freezes region/process identity, checks complete reads per block and publishes no partial file after a short read, cancellation or failure. The chosen action fixes the backend without automatic fallback. A real R3 GUI export has controlled-byte and hash verification; R0 reads have not been accepted with a loaded driver. Reading a running process in blocks does not guarantee a single-time coherent snapshot.

07 / MONITORING

API, ETW, syscall and callback monitoring

API Monitor has separate x86/x64 agents, 641 shared JSON definitions, direct cross-bitness injection and a session broker for children. Coverage shows installed, waiting, excluded and failed entries. Async I/O separates submission, completion and cancellation. Raw records entry only; direct syscalls, arbitrary COM and calls before monitoring are outside guaranteed coverage. TSV exports visible rows, with losses counted separately.

ETW uses payload-associated process/thread identity while retaining event-header identity. Structured fields, arrays and TraceLogging schemas follow their layouts; truncation remains a coverage gap. Syscall correlation uses raw QPC, CPU and StackWalk evidence. A compatible stub shape, syscall byte sequence or RWX page alone does not establish malicious intent or a tool version.

Kernel callback monitoring has separate Control/Query/Read operations and consumer cursors. Pause freezes UI submission while bounded collection continues. It observes KSword runtime callbacks, separately from registered-callback inventory and AskUser interception rules.

08 / FILES

File details and R0 deletion

Single-file and batch details stage metadata changes. “Save all changes” checks identity, creates backups, writes and reads back results. Timestamps, attributes, ADS, EA, security, reparse data, filesystem features and PE resources have separate limits; risky edits require backups. Signatures show WinVerifyTrust results, string searches scan the file and Hex navigation reads by offset.

R0 deletion returns per-stage results. IRP presets use managed opens and submit at the base filesystem. Ordinary, ignore-share and forced modes retain their distinct confirmation and risk. Clearing image/cache section members does not guarantee active-mapping consistency. Completion requires a path check after closing; builds and mocks cannot prove live deletion safety.

The file context menu hides unavailable actions and empty submenus. A single .exe can offer System, TrustedInstaller, administrator or standard-user launches according to token capability. Launches preserve the interactive session and target-user environment; failed identity selection never silently inherits a higher privilege. Standard-user and menu regressions passed; administrator/System/TI success probes were not run on the unelevated validation host.

09 / KERNEL

Callback removal and kernel knowledge

V3 callback inventory retains registration subtype, source, identity and trust. Object removal needs the real RegistrationHandle; Registry uses a Cookie. EX requests re-enumerate before the public API call and verify afterwards. Extended removal remains candidate-scoped. The experimental unlink menu is gone; ETW/EMP rows without recovered handles stay unavailable.

A Minifilter child action unloads its owning filter, including all callbacks and instances, and the filter may refuse. The knowledge center has 71 topics in 12 categories, live evidence and read-only routes. Available means the route is implemented, not that every permission, profile or field is available on the current machine.

10 / VIRTUALIZATION

Intel EPT and AMD SVM/NPT

The code includes Intel residency, MSR bitmaps, exit emulation and EPT views/policies, plus an experimental AMD SVM/NPT backend. The title bar and KVM Dock share admission checks covering hardware, per-CPU self-tests, power generation, topology and unload protection. A preference cannot bypass unknown outer hypervisors or Hyper-V/VBS conflicts.

EPT ENFORCE currently returns UNIMPLEMENTED.

The old #PF path is not a completed durable-denial feature. WATCH_ONCE captures first-touch evidence and then opens the page; it does not log every later write. An execution view is not ordinary data freezing or general process isolation.

11 / NESTED

Nested implementation and evidence

Intel has vmcs12, exit reflection, shadow EPT and descendant page/region leases. Support, preparation, all-core arming and transient L2 execution are reported separately. AMD has general VMCB/NPT handling, event coordination and incident capture, but remains experimental PARTIAL.

Saved AMD evidence covers selected single/8-core cycles and a short 32-core resident run. Serial fixed probes do not prove concurrent inner OS execution. Complete L2 boot has triple-fault/host-crash records and candidates awaiting retest; full OS compatibility is not claimed. The seven-step topology demo remains a historical Intel/Hyper-V example, not an AMD or universal topology.

12 / R-1

R-1 memory and target operations

R-1 memory offers physical/virtual reads and writes, translation and PID-based lookup. If the private window is unavailable, reads may report fallback and writes are unavailable. Snapshots bind address, CR3/PID, mode and generation. Target actions still depend on identity, mapping, policy and residency. A successful request does not prove termination or changed bytes.

13 / DEBUGGERS

CE / x64dbg and clipboard protection

The shared debugger backend owns identity, memory, contexts, HVM selection and its own resources; CE/Titan use real Windows stop events. Execution breakpoints use supported EPT or logged Shadow INT3 fallback. Stealth mode rejects visible DR/PAGE_GUARD fallback. CE and Titan have different data-breakpoint limits. Shadow code writes require private/COW pages and do not freeze ordinary data.

Clipboard protection chooses the agent by target bitness and shares PID leases with API Monitor. Policies can update in place. Protection is counted only after Hook readiness; a rule match or successful injection does not prove global coverage. Cross-user, direct-call and protected-target limits remain.

14 / LIGHT

Light investigation workbench

Native Win32 x64 Light provides lazy secondary pages, entity routes, PID plus creation-time identity and cross-process driver leases. Exiting Light does not stop a driver that was already running; R3 browsing and evidence continue without the driver.

The command box navigates modules/entities by default; only a leading ! executes a shell command. Successful exports enter evidence sessions with recent row diffs, JSON/TSV and user-directory redaction. Memory history replays successful local snapshots; its native editor has no Qt assembler. Process columns distinguish unknown, warm-up and real zero. I/O rates are not physical disk throughput.

15 / UI & COMPATIBILITY

Search, window control and compatibility

Global UI search, snapshot differences and themed controls are integrated into the workbench. Both Window and Misc offer input/DWM ordering controls. Composition order and native input order are distinct. Cross-UIAccess Win32k writes match only the exact win32kfull 10.0.26100.9022 profile; mocked receipts do not verify real clicks.

The driver/Launcher upper OS-build gate is removed. Minimum build 16299 and per-feature capability/layout/profile checks remain. Removing a startup ceiling adds no verified profile for an unknown system and guarantees no feature.

Process settings and history retention

The gear opens a separate process-list settings dialog for enumeration, refresh, R0 comparison and background recording. Activity history offers stop recording, keep all, or keep the latest samples, defaulting to 50. Reducing the limit trims immediately; stopping recording retains existing samples.

SOS rescue desktop

Run matching Taskbar and KSword builds, enter S O S Enter on a physical keyboard, and approve UAC on the original desktop. A new elevated KSword instance then opens on a restricted private Win32 desktop. Its return button or physical Ctrl+Alt+Shift+F10 restores the original desktop; existing windows and unsaved sessions are not migrated. This is separate from Winlogon/UAC secure desktops, and R3 cannot prove virtual-HID or driver-level input origins. Basic entry/return has saved live evidence; lock screens, focus interference and input variants need separate acceptance. See SOS rescue desktop guidance.

Shared page structure and Taskbar overview

Standard controls, table tools, secondary details, parameter workspaces and nested tabs are progressively adopting shared themes/layouts while retaining field sources, professional views, copy/export and snapshot semantics. Recent fixes address transparent surfaces, menu/search states, child-page navigation and rounded boundaries. Shared rules do not establish visual acceptance of every existing page.

The grid button on the separate Taskbar opens an overview from the application's real page catalog, arranged by top-level and nested pages with name/path search and direct navigation. Adjustable backdrop blur falls back to transparent navigation when system composition is unavailable; RGB remains an auxiliary accent. Use matching Taskbar/application builds. Live blur, DPI and the full navigation matrix still require scenario-specific acceptance.

17 / OPERATOR NOTES

Working sequence

    Use matching artifacts and inspect status first.

    Record system, driver, profile, target identity and capability. Unsupported or missing data is not “no anomaly”.

  2. 2
    Observe and export before modifying.

    Staged memory/file edits are not completed writes. Keep confirmations and recovery records for removal, deletion and HVM actions.

  3. 3
    Check results and coverage.
