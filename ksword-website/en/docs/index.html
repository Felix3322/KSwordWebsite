01

Decide whether this operation requires R0

No driver required first

Browsing ordinary process lists, viewing basic file information, reading most system configuration, viewing logs, and using read-only R3 pages.

Driver required first

CE R0/HVM paths, R3/R0 cross-view, kernel memory and page tables, driver-object evidence, callback operations, and any feature explicitly marked R0. Without a driver, CE can retain native function tables; [KSword Connected] does not mean R0 is active.

Do not treat an enabled button as proof that a feature is actually using R0.

The real requirements are that the client can open \\.\KswordARKLog, the current driver supports the target IOCTL, and the required DynData and Capability are ready.

03

“Service started” does not mean the driver is usable

Service layer
  • The service exists
  • StartService succeeds
  • ImagePath points to the correct SYS
Communication layer
  • \\.\KswordARKLog opens
  • Protocol and IOCTL versions match
  • The required Capability is available

After loading the driver, check Driver Status first and DynData second. Do not begin by repeatedly clicking feature buttons.

The device cannot be opened

Check elevation, service state, signature, SYS path, and device creation. DynData is not yet the issue.

The device opens but the old driver does not support the operation

Communication exists, but the SYS lacks the control code. Restore the driver from the same release.

The IOCTL returns a failing NTSTATUS

The request reached the driver. Continue with R0 logs, target state, and parameters instead of reinstalling the service.

Basis: DriverClient::open() and deviceIoControl().

04

DynData determines which R0 features can run safely

Loaded means only that the channel exists. Features that depend on kernel structure offsets, global RVAs, function RVAs, or type sizes also require a profile that matches the current kernel identity and is accepted by the driver.

Matched

The local profile matches the current module identity; still verify Accepted items and Capability.

Missing items

Disable only features that depend on those fields. Do not interpret one missing item as total R0 failure.

The old driver does not support V4 queries

The application is newer than the driver. Copying a JSON file cannot repair a protocol mismatch.

Profile mismatch

Do not reuse offsets from a “similar” Windows version. Incorrect offsets may be more dangerous than a safe feature downgrade.

After a Windows update, check DynData before making kernel changes.

Even the same Windows major version may use a different kernel build and PDB identity.

Basis: matched, accepted, missing, and capability states in KernelDock.DynData.cpp.

05

CE, TitanEngine and x64dbg/x96dbg

Launch matching debugger integrations from KSword’s process actions and verify target identity, bridge readiness and the actual backend. Shared DebuggerBackend/ now covers memory, context, suspend/resume, allocation/protection and Windows debug-event adaptation. The old four-memory-API description no longer applies.

  • CE has 15 SDK hooks; WOW64 context and CE VEH/DBVM are outside this native Windows adapter scope.
  • Fallback from HVM/EPT is policy-controlled; actual path, fallback counts and errors are reported separately.
  • Shadow code writes change the execution view, not ordinary data reads. Active patches/breakpoints constrain mode changes and exit.
  • Use runtime diagnostics for R0/HVM/native routing; a selected mode alone does not prove activation.

Debug sessions retain real Windows stop events; verify restoration of owned breakpoints, patches and resources on exit.

06

Process operations cannot rely on PID alone

Refresh before terminating, suspending, changing protection, hiding, or applying batch operations.

KSword identifies processes with PID + creationTime100ns because exited PIDs are reused. A row that has remained on screen for a long time may no longer represent the original process.

  • Context-menu and batch actions on an application-group row apply to every real member in the group.
  • The friendly application view and parent-child tree show different relationships. Switch back to the parent-child tree before reasoning about process ancestry.
  • Do not use PID 0, PID 4, the current KSword process, or critical system processes as write-operation test targets.
  • Before hiding a process, record its path, creation time, and original PID. Recovery depends on records maintained by the driver, so do not unload the driver before recovery completes.
  • A difference between R3 and R0 enumeration is evidence. Do not delete or hide objects merely to make the lists match.

Basis: process identity, application-group batch actions, and R0 visibility records.

07

Snapshots, staged edits and actual readback

Hex, disassembly, text and comparison share one read snapshot. Editing, assembly and undo/redo change the local buffer; apply explicitly through the owning page and confirm actual readback.

  1. Verify identity, R3/R0/R-1/DDMA backend, address, CR3 and x86/x64 architecture before reading.
  2. Preview old/new bytes and cover complete decodable instructions. Common Intel instructions and local labels are supported; CE alloc/registersymbol scripts are not.
  3. Recheck original bytes/session before writing and verify each authorized difference block. Conflicts, partial or unknown readback are not overall success.

DDMA is read-only in the ordinary process viewer. Dedicated DDMA requires explicit scratch disk/LBA, debugger-state and pass-through checks plus sector restoration; emulated guest DMA does not prove bypass of host translation.

Full documentation and limitations →

Dump a single memory region

Open Process details → Memory → Memory regions, or the main Memory → Memory regions page, then choose the R3 or R0 region-dump action. The selected backend stays fixed with no automatic fallback. Output is raw .bin bytes matching the region length, rather than a whole-process .kmdump or Windows minidump.

Each chunk rechecks process identity and region metadata. Short reads, partial results, zero-filled failure data and length mismatches fail the export. Reading can be cancelled; atomic saving never publishes an incomplete file. Final commit cannot be withdrawn once it begins. Reading a running process in chunks is not a single-time snapshot.

The committed record includes a controlled R3 export through the real GUI. R0 routing has source and regression checks, without a live-driver read in that record. Entries, save semantics and validation →

08

Unlocker does not automatically close every holder

You must manually confirm the exact process and handle.

The automatic no-selection unlock path was intentionally removed to avoid closing the wrong process or a related handle. Closing a remote handle can crash the owner, discard unwritten data, or leave it in an abnormal state.

  1. 1
    Inspect the file-holder list first.

    Verify the process path, PID, creation time, and handle type.

  2. 2
    Prefer a normal application exit.

    Close a handle only when the owner cannot release it normally.

  3. 3
    Handle one confirmed owner at a time.

    Refresh the holder list after each action.

  4. 4
    Then move, delete, or replace the file.

    An empty holder list does not prove that file contents have been safely flushed.

  • If mapped-file lookup shows Unsupported, the current driver lacks the interface; it does not prove that no process maps the file.
  • Before recovery, deletion, integrity-label changes, or forced operations, copy the original file or record its metadata.

Basis: the manual process-selection safety change in Unlocker and R0 mapped-file queries.

09

Collect evidence before modifying kernel state

Callback removal, hook modification, and driver unloading all change the investigated system.

Export the current address, owning module, signature, source view, and timestamp first. Refresh after the change instead of reasoning from the old table.

  • Callback and module states change. Refresh immediately before the operation and confirm that the target still belongs to the same module.
  • Removing callbacks from third-party security drivers can break their internal state. Test only in a rollback-capable virtual machine.
  • The driver-debug-output page shows only messages allowed by the active kernel filter. No visible log does not prove that code did not run.
  • Preserve Partial and Unsupported states instead of filling missing fields with “normal.”
  • Before unloading KswordARK, close CE, stop continuous monitoring, and restore temporary state maintained by the driver.

10

Some network features change system state

Packet capture and NIDS

Primarily observational. A NIDS alert is not an automatic blocking conclusion; correlate it with connections, processes, and the timeline.

Connection termination and rate limiting

Directly affect active traffic. Record PID, endpoints, and protocol first.

HTTPS analysis

May involve a local proxy, system proxy configuration, and certificate state, so it is not purely read-only.

  1. Record the current Windows proxy settings before enabling HTTPS analysis.
  2. When finished, stop the proxy in KSword and verify that the system proxy was restored.
  3. If browsers lose network access after an abnormal KSword exit, check the system proxy and local listening port first.
  4. Do not run multiple tools that modify the system proxy at the same time.

11

“Installed successfully” and “runtime protocol works” are different states

  • A marketplace package must be downloaded, verified, and extracted completely. The runtime entry is defined by runtime and entrypoint in plugin.json; a source file is not automatically executable.
  • Executable plugins report ready, progress, results, and completion through JSON Lines. Raw text or invalid JSON is not converted into structured scan results.
  • If the scan page remains in a waiting state, inspect the plugin process, exit code, stderr, and protocol events before repeatedly reopening the UI.
  • Cancellation guarantees only that the host starts its terminate or cancel flow. Child processes and external state created by the plugin still require inspection.
  • Close running instances before updating a plugin so old DLLs or EXEs are not still locked.
The CE plugin is a hybrid executable, not a normal scanner plugin.

It has independent driver-check, launch, tab, and info commands. Connected R0/HVM paths maintain a driver session; disconnected paths can retain native routing.

Basis: PluginHost.cpp, plugin manifests, and the scan-table protocol.

12

Prepare rollback material before editing the registry, startup entries, services, or disks

Registry

Export the target key before editing it. Preserve value type, data, and permissions, not only a screenshot.

Startup entries and services

Record the original start type, ImagePath, account, and dependencies. Confirm that a service is not a shared driver service before deleting it.

Disk editing

Save the target range or a complete image before any raw-sector write. Do not test writes on the system disk.

  • “Optimization” does not mean safe for every machine. Apply changes individually and reboot-test before continuing.
  • A successful service stop does not prove that its driver object, device, or filters were cleaned up safely.
  • Undoing a disk write depends on saved original bytes, not UI history.

Stage registry changes before applying them

Current main organises multi-value editing as a document and change plan. Edit by registry type while preserving raw bytes, preview differences, recheck source values, then apply and read back. Staging a plan does not change the system. Preserve source conflicts and failed readback as actual errors, and export the original key before editing.

13

R0 changes require a controlled shutdown order

  1. 1
    Stop new scans, monitors, and plugin tasks.

    Wait for Current Operations to clear or explicitly cancel them.

  2. 2
    Close CE and plugins that own KswordARK device handles.

    Prevent an old session from calling a driver that is being unloaded.

  3. 3
    Restore temporary changes.

    This includes hidden processes, proxy settings, test state, and other recoverable system changes.

  4. 4
    Export logs and evidence.

    Keep the refreshed post-change result together with the pre-change snapshot.

  5. 5
    Unload the driver or exit KSword last.

    Do not treat driver unload as an automatic rollback for every kernel modification.

14

Map each symptom to the correct layer

Every R0 page is unavailable

Check the device handle, elevation, service, and signature before changing profiles.

Only some R0 pages are unavailable

Check the feature IOCTL, Missing items, and Capability. The whole driver usually has not failed.

CE starts but does not open the target automatically

Bridge initialization or delayed openProcess(pid) failed. Close CE and relaunch it from KSword.

CE reads but cannot write

Check driver policy, page state, selected backend and actual fallback; current adapters include allocation/protection interfaces.

The file still appears locked

Refresh the holder list and check for mappings, a second handle, or a newly created process instance.

Network access fails after leaving the network tools

Check the system proxy, certificate state, and local proxy process before resetting the network stack.

A plugin installs but produces no result

Inspect the manifest entry, exit code, stderr, and JSONL events.

Many features show Unsupported after an update

Confirm that the EXE, SYS, profiles, and plugins came from the same release.

Include at least the following in an Issue

Version combination

The source release for KSword, SYS, plugins, and profiles.

Target identity

PID, path, creation time, and Windows build.

R0 state

Device-open result, protocol error, Missing items, and Capability.

Exact error

Win32 Error, NTSTATUS, event code, and timestamp.

Execution order

The startup order for the driver, KSword, plugins, and CE, including whether files were replaced during the session.

ETW, Syscall and WinAPI sessions

Monitoring provides per-process ETW, Syscall, x86/x64 API agents, WMI and ETW session management. Injection chooses a DLL matching the target architecture; agent sessions carry ownership and readiness.

  • ETW retains provider, header PID/TID and correlated target identity; image enumeration is not relabeled as loading.
  • Syscall depends on time/stack correlation; compatible-stub detection does not prove all direct syscalls were captured.
  • Interpret readiness, revisioned coverage, Raw entries, asynchronous completions and loss separately; a started session does not observe every API.

Select target/rules, start, verify coverage, then interpret and export.

Intel and experimental AMD virtualization

The workspace includes Intel VMX/EPT, nested VMX/EPT composition, hooks and R-1 memory, plus AMD SVM/NPT and nested SVM preparation, self-test, residency and evidence flows.

  1. Verify hardware, outer hypervisor, capabilities and rejection reasons.
  2. Prepare → all-CPU self-test → residency; verify mode, generation and actual per-CPU state.
  3. Stop and teardown through the lifecycle, retaining states/errors. Partial residency is not complete success.

Full inner multicore OS boot and performance on AMD await acceptance. ENFORCE is published as unimplemented; a policy table does not prove enforcement.

Light workspace and evidence

Light remains native Win32 without Qt, with on-demand secondary pages, process telemetry, entity navigation and evidence sessions. It does not promise full-edition parity.

  • The command box defaults to pid/tid/hwnd/file/reg/net navigation; leading ! explicitly enters command execution.

  • Keep unknown/partial states distinct from actual zero.

Windows and exact-offset support

The Qt path uses minimum build 17763 and the R0 startup protocol uses 16299; these are different component gates. The product targets Windows 10/11 x64.

Launcher and driver upper-build gates were disabled on 2026-10-03. New systems still depend on exact PE/RSDS/PDB profiles and feature, layout and address checks.

Collection-only means identities can be collected, not that full offsets exist. Intake validates valid=true before formal corpus import.

20

MCP setup and GUI connection

Current main connects an external stdio sidecar to the real Qt GUI through a local named pipe. It provides page discovery, control trees, table slices, text reading and native control actions. Special controls use registered read-only adapters.

  1. Confirm that the downloaded GUI build supports MCP, then install the matching sidecar and Python dependencies. Older packages may predate the feature.
  2. Enable the current service under Settings → MCP. Auto-start is off by default. Paths and startup preferences use Apply/Cancel; starting or stopping this session takes effect immediately.
  3. Configure the client with actual full Python, sidecar and GUI paths. --ksword-exe defaults to --startup-policy fail; only an explicit auto policy starts the GUI on a tool call. PID mode requires the actual target PID.
  4. Read hello, pages and snapshot before using current objects. Select rows against the latest table revision. Destroyed or recreated controls require fresh object IDs.
Verify registration, discovery, GUI connection and business success separately.

accepted / dispatched describe control calls. Read the original page to check background tasks, confirmation dialogs and results. Actions, field edits and row selection require explicit confirmation and retain existing business confirmation flows.

  • Use boolean true/false to set a standard checkbox. Toggle reverses its value; setting the existing value leaves it unchanged. Table-cell checkboxes require their model capabilities.
  • Connections check user, session and integrity. A UAC startup exception is bound to this client's actual PID and creation time. There is no TCP service, automatic restart of existing instances or retry of business requests.
  • The operation log keeps the latest 1,000 records in memory, recording methods and receipts without arguments or read results. It is discarded on exit.

CLI/IOCTL tools can be configured independently of the GUI. Verify their privileges and outcomes as described below.

21

CLI and raw IOCTLs

CLI covers the 66-item Light R3 migration manifest, including process, file, registry, service, network, monitoring, object-namespace and security-evidence commands. Elevation requirements depend on the R3 command. R0 commands generally need the matching loaded driver.

KswordCLI.exe help
KswordCLI.exe help process
KswordCLI.exe help system ioctl call

--json preserves backend, success/partial/unsupported/failed, data and diagnostics. Keep the actual exit code; empty results and partial output are not complete success. Pure R3 commands default to R3 without an automatic R0 fallback.

system ioctl decode only decodes a number and sends no request. system ioctl call uses the existing ArkDriverClient to send one bounded request to the fixed KSword control device. Every call requires --confirm; input and output are each limited to 1 MiB. Codes and buffer ABI come from matching shared/driver/ definitions. Transport success does not establish the response's business status. It does not install drivers, elevate or resend.

For MCP, check the path with ksword_cli_status, then read native help with ksword_cli_help. Arbitrary commands and raw IOCTLs require confirmed=true; any native --confirm is still required. A timeout can leave the outcome unknown; read state before deciding what to do next.

22

Reports and permission workbench

Process details → Process Detail Evidence → Structure report preserves section, type and field hierarchy. Search includes collapsed descendants and full raw values. Section copying, full copying and export use the same canonical document without truncating it to the current expansion or filter. Unloaded or producer-truncated catalog entries retain their original limits.

The permission workbench includes accounts, groups, direct LSA rights, token comparison, access diagnostics, logon sessions, identity launch and manual snapshots. Confirm the SID, process creation time and actual token before operations, then inspect readback after changes.

  • Direct LSA assignments differ from a process's effective token. Policy edits do not immediately rewrite existing tokens.
  • AccessCheck diagnoses the selected token, descriptor and mask. It does not guarantee that a real file, registry or service operation will succeed.
  • Unreadable, absent and equal evidence remain distinct. Manual snapshots are not an atomic snapshot of every system object.

Taskbar page overview

The main title bar searches page paths and controls. The grid button on the independent Taskbar opens a page overview: one column per top-level Dock, with nested pages indented. Search names or full paths, press Enter for the first result, or Esc to close.

The overview reads the GUI's actual page catalog, restores outer-to-inner Tab paths and rechecks visibility and availability. Refresh stale catalogs. RGB is an auxiliary accent; unavailable blur falls back to a readable transparent layout. The SOS keyboard entry and page navigation remain separate functions.

24

Reset-free CKS research

The third CKS subpage, Reset-free research, separates two candidates: re-establishing enrollment before boot, and an app-preserving repair installation that might affect enrollment. Neither has a verified successful workflow or constitutes a supported reset-free enrollment procedure.

Existing disabled enrollment, boot licensing, PK/KEK trust and base-policy signatures are separate gates. Licensed=1, a deployed policy or a successful normal refresh does not prove that CKS is effective. Verification requires actual CKS state, target-driver loading, CI events and persistence after reboot and updates.
