01

先判断这次操作是否需要 R0

不需要先加载驱动

浏览普通进程列表、查看基础文件信息、读取大部分系统配置、查看日志和只读 R3 页面。

必须先加载驱动

CE 的 R0/HVM 路径、R3/R0 Cross-view、内核内存与页表、驱动对象证据、回调操作以及任何明确标为 R0 的功能。CE 未连接驱动时仍可保留原生函数表；[KSword Connected] 不表示 R0 已启用。

不要用“按钮能点”判断功能是否真的走 R0。

实际标准是客户端能打开 \\.\KswordARKLog，目标 IOCTL 被当前驱动支持，并且该功能所需的 DynData/Capability 已就绪。

检查模式仅核对清单，不启动主程序，也不生成采集包。需要 R0 或受保护模块采集时按提示提升权限。

03

“服务已启动”不等于驱动已可用

服务层
  • 服务存在
  • StartService 成功
  • ImagePath 指向正确 SYS
通信层
  • 能打开 \\.\KswordARKLog
  • 协议/IOCTL 匹配
  • 功能所需 Capability 可用

驱动加载后，先看 Driver Status，再看 DynData。不要先去具体功能页反复点击按钮。

设备打不开

先查管理员权限、服务状态、签名、SYS 路径和设备创建。此时 DynData 还不是问题。

设备能打开但旧驱动不支持

说明通信存在，但当前 SYS 没有该控制码。换回同一 Release 的驱动。

IOCTL 返回失败 NTSTATUS

设备和协议都已到达驱动，继续看 R0 日志、目标状态和参数，不要再重装服务。

依据：DriverClient::open()、deviceIoControl()。

04

DynData 决定的是“哪些 R0 功能能安全运行”

设备 Loaded 只代表通道存在。依赖内核结构偏移、全局 RVA、函数 RVA 或类型大小的功能，还要求 profile 与当前内核身份匹配并被驱动接受。

Matched

本地 profile 与当前模块身份匹配，仍需看 Accepted items 和 Capability。

Missing items

只禁用依赖这些字段的功能；不要把单项缺失误判为整个 R0 失效。

旧驱动不支持 V4 查询

主程序比驱动新。不要手工复制一个 JSON 试图解决协议缺失。

Profile 不匹配

不要套用“相近 Windows 版本”的偏移。错误偏移可能产生比安全降级更严重的结果。

Windows 更新后第一次运行，先检查 DynData，再做内核修改。

同一主版本的 Windows 也可能更换内核构建和 PDB 身份。

依据：KernelDock.DynData.cpp 的 matched、accepted、missing 和 capability 状态。

05

CE、TitanEngine 与 x64dbg/x96dbg

从 KSword 的进程入口启动配套调试器，核对目标身份、桥接就绪与实际后端。公共 DebuggerBackend/ 已覆盖内存、上下文、挂起/恢复、分配/保护及 Windows 调试事件适配，旧版“仅接管四个内存 API”的描述已不适用。

  • CE 当前有 15 个 SDK Hook；WOW64 上下文、CE VEH/DBVM 不在本版原生 Windows 调试适配范围。
  • HVM/EPT 不可用时，是否允许回退由策略控制；实际路径、回退次数与错误单独展示。
  • 代码 Shadow 修改只改变执行视图，不能把普通数据冻结当作隐形数据修改；活动补丁/断点限制模式切换和退出。
  • R0/HVM 与原生路由均应看运行态诊断，不能凭模式名称断言已启用。

调试会话保留真实 Windows 停止事件；退出时核对自有断点、补丁与资源的还原。

06

进程操作不能只看 PID

结束、挂起、保护级别、隐藏或批量操作前先刷新。

KSword 用 PID + creationTime100ns 识别进程，因为退出后的 PID 会被复用。停留很久的旧行可能已经不是原进程。

  • 应用聚合行的右键和批量动作会作用于组内全部真实成员，不是只操作当前显示的一行。
  • “进程友好视图”和父子树视图表达不同关系；在判断父进程链前切回父子树。
  • PID 0、PID 4、当前 KSword 进程和关键系统进程不要作为写操作测试目标。
  • 隐藏进程前记录路径、创建时间和原 PID；恢复依赖驱动保存的记录。恢复完成前不要卸载驱动。
  • R3 与 R0 枚举不一致是证据，不要为了“让列表一致”直接删除或隐藏对象。

依据：进程 identity、应用聚合批量动作、R0 visibility 记录。

07

读取快照、暂存编辑与实际回读

Hex、反汇编、文本和对比视图使用同一份读取快照。修改、汇编、撤销/重做只改变本地缓存；必须通过所属页面显式应用，成功以实际回读为准。

  1. 核对目标身份、R3/R0/R-1/DDMA 后端、地址、CR3 与 x86/x64 位数，再读取。
  2. 选择修改范围，预览旧/新机器码，覆盖完整可解码旧指令。支持常用 Intel 指令和局部标签，不支持 CE alloc/registersymbol 等脚本。
  3. 写前复核原字节和会话，检查每个授权差异块的回读。冲突、partial 或未知回读不得当作整体成功。

普通进程查看器 DDMA 保持只读。独立 DDMA 入口涉及显式暂存磁盘/LBA、调试器状态、透传和扇区恢复；虚拟机模拟 DMA 不证明绕过宿主翻译。

完整文档与限制 →

只导出一个内存区域

进程详情 → 内存 → 内存区域，或主导航 → 内存 → 内存区域，右键选择“R3导出此区域Dump…”或“R0导出此区域Dump…”。动作固定所选后端，不自动回退；输出是与区域长度一致的原始 .bin 字节，不是整进程 .kmdump 或 Windows minidump。

每块读取复核进程身份和区域元数据；短读、partial、补零或长度不一致会失败。读取阶段可取消，原子保存不会发布半个目标文件；进入最终提交后不能撤回。运行中进程的分块读取不保证所有字节来自同一时刻。

已提交记录包含真实 GUI 的受控 R3 导出；R0 固定通道经源码与回归核对，记录中未加载驱动实读。入口、保存语义与验证 →

08

文件 Unlocker 不是“自动关闭所有占用”

解锁时必须手动确认具体进程和句柄。

项目特意取消了无选择的自动解锁路径，避免关闭错误进程里的同名或相关句柄。关闭远程句柄可能让持有进程崩溃、丢失未写入数据或进入异常状态。

  1. 1
    先查看文件占用列表。

    核对进程路径、PID、创建时间和句柄类型。

  2. 2
    优先正常退出持有程序。

    只有无法正常释放时才使用关闭句柄。

  3. 3
    一次只处理一个确认过的持有者。

    每次处理后重新刷新占用列表，再决定是否继续。

  4. 4
    再执行移动、删除或替换。

    不要把“列表暂时为空”当作文件内容已经安全落盘。

  • 映射文件反查显示 Unsupported 时，只能说明当前驱动缺接口，不能证明没有进程映射该文件。
  • 文件恢复、删除、完整性标签和强制操作前，先复制原文件或记录元数据。

依据：Unlocker 必须手动选进程的防误触改动、文件映射 R0 查询。

09

内核页先采证，再修改

回调移除、Hook 修改和驱动卸载都应视为会改变被调查系统。

先导出当前地址、所属模块、签名、来源视图和时间，再执行修改。修改后重新刷新，而不是继续使用旧表格判断结果。

  • 回调列表和模块状态会变化；操作前最后刷新一次，并核对目标仍属于同一模块。
  • 删除第三方安全驱动回调可能破坏其内部状态，测试应放在可回滚虚拟机。
  • 驱动调试输出页只显示通过当前内核筛选器的消息；“没有日志”不等于代码没有执行。
  • 页面显示 Partial/Unsupported 时保留原始状态，不要把缺失字段补成“正常”。
  • 卸载 KswordARK 前，先关闭 CE、停止持续监控并恢复由驱动维护的临时状态。

10

网络页面里有些功能会改变系统状态

抓包与 NIDS

主要用于观察。NIDS 告警不是自动阻断结论，需要结合连接、进程和时间线确认。

终止连接与限速

会直接影响现有业务连接；执行前记录 PID、端点和协议。

HTTPS 分析

可能涉及本地代理、系统代理配置和证书状态，不是纯只读功能。

  1. 启用 HTTPS 分析前记录当前 Windows 代理设置。
  2. 结束后先在 KSword 中停止代理，再检查系统代理是否恢复。
  3. KSword 异常退出后若浏览器突然无法联网，先查系统代理和本地监听端口。
  4. 不要同时运行多个会修改系统代理的工具。

11

插件“安装成功”和“运行协议正常”是两件事

  • 市场插件包应完整下载、校验并解压；不要把源码文件当作运行入口，实际入口由 plugin.json 的 runtime/entrypoint 决定。
  • 可执行插件通过 JSON Lines 报告 ready、进度、结果和完成事件；原始文本或不合法 JSON 不会自动变成结构化扫描结果。
  • 扫描页长时间停在等待状态时，先看插件进程是否退出、stderr 和协议事件，不要只重开 UI。
  • 取消任务只保证宿主发出终止/取消流程；插件自身创建的子进程或外部状态仍需检查。
  • 更新插件时先关闭其运行实例，避免旧 DLL/EXE 仍被占用。
CE 插件是 hybrid executable，不是普通扫描插件。

它有独立的 driver check、launch、tab 和 info 命令；R0/HVM 已连接时维护驱动会话，未连接时可保留原生路由。

依据：PluginHost.cpp、插件 manifest 和 scan-table 协议。

12

注册表、启动项、服务和磁盘编辑都先准备回滚材料

注册表

修改前导出目标键，不要只截屏。值类型、数据和权限都要保留。

启动项/服务

禁用前记录原启动类型、ImagePath、账户和依赖关系。删除服务前先确认不是共用驱动服务。

磁盘编辑

任何原始扇区写入前先保存目标范围或完整镜像；不要在系统盘上测试写入。

  • “优化”不代表对所有机器安全。逐项应用，重启验证后再继续下一组。
  • 服务停止成功不代表其驱动对象、设备或过滤器已安全清理。
  • 磁盘写入后的撤销依赖你保存的原始字节，不依赖 UI 历史记录。

注册表工作台先暂存，再应用

当前主线把多值编辑组织成文档与变更计划：按注册表类型编辑并保留原始字节，先预览差异，再核对源值、应用并回读。暂存或计划显示完成不代表系统已改变；源值冲突和回读失败保留为真实错误。修改前仍需导出原键。

13

做过 R0 修改时，退出顺序也有要求

  1. 1
    停止新的扫描、监控和插件任务。

    等待 Current Operations 清空或明确取消。

  2. 2
    关闭 CE 和其他持有 KswordARK 设备句柄的插件。

    防止旧会话继续调用正在卸载的驱动。

  3. 3
    恢复临时修改。

    包括隐藏进程、代理设置、已知的测试状态和可恢复的系统改动。

  4. 4
    导出日志和证据。

    修改后的刷新结果与修改前快照应一起保存。

  5. 5
    最后再卸载驱动或退出 KSword。

    不要把卸载驱动当作自动恢复所有内核修改的方法。

14

按症状定位到正确层级

所有 R0 页面都不可用

先查设备句柄、管理员权限、服务和签名，不要先换 profile。

只有部分 R0 页面不可用

查该功能的 IOCTL、Missing items 和 Capability，通常不是整个驱动失败。

CE 能启动但没有自动打开目标

桥接 DLL 初始化或延迟 openProcess(pid) 失败。关闭后从 KSword 重启。

CE 读正常但写失败

检查驱动策略、页状态、所选后端与实际回退；当前适配器已接入分配/保护接口。

文件仍提示占用

刷新占用列表，确认是否还有映射、第二个句柄或新创建的进程实例。

网络工具退出后无法联网

先查系统代理、证书和本地代理进程，不要先重置整个网络栈。

插件安装完成但没有结果

查看 manifest 入口、插件退出码、stderr 和 JSONL 协议事件。

更新后出现大量 Unsupported

检查 EXE、SYS、profiles 和插件是否来自同一个 Release。

提交 Issue 至少附带

版本组合

KSword、SYS、插件和 profile 来源。

目标身份

PID、路径、创建时间和 Windows Build。

R0 状态

设备打开结果、协议错误、Missing items 和 Capability。

精确错误

Win32 Error、NTSTATUS、事件码和发生时间。

操作顺序

驱动、KSword、插件、CE 的启动顺序，以及中途是否替换文件。

15

ETW、Syscall 与 WinAPI 会话

监控模块提供进程 ETW、Syscall、x86/x64 API Agent、WMI 和 ETW 会话管理。自动注入按目标位数选 DLL；同一目标的 Agent 会话具有所有权与就绪状态。

  • ETW 保留 Provider、事件头 PID/TID 与关联目标身份；映像枚举不伪称加载。
  • Syscall 依赖时序/栈关联；兼容桩检测不证明所有直接系统调用均被记录。
  • Hook 就绪、版本化覆盖、Raw 入口、异步完成和丢事件分别解读；启动成功不保证所有 API 可观测。

先选目标与规则，启动后核对覆盖，再解释和导出事件。

16

Intel 与实验性 AMD 虚拟化

虚拟化工作区包含 Intel VMX/EPT、嵌套 VMX/EPT 合成、Hook 与 R-1 内存，也接入 AMD SVM/NPT 和嵌套 SVM 的准备、自检、常驻及证据流程。

  1. 先核对硬件、外层 hypervisor、能力与拒绝原因。
  2. 准备 → 全核自检 → 常驻；确认模式、代次和每个 CPU 的实际状态。
  3. 停止后按正常生命周期释放，保留状态和错误。部分常驻不能按完整成功处理。

AMD 完整内层多核 OS 启动与性能仍待验收。ENFORCE 发布为未实现，不能把策略表存在宣传为全量处置已生效。

17

Light 工作台与证据

Light 保持原生 Win32、无 Qt 依赖，提供按需二级页、进程遥测、跨模块实体跳转与证据会话。功能覆盖不承诺与完整版本完全相同。

  • 命令框默认解释 pid/tid/hwnd/file/reg/net 等导航；前导 ! 显式进入命令执行。
  • 证据会话记录成功导出，支持快照、最近两次行级差异、JSON/TSV 与用户路径脱敏。
  • 跨进程驱动租约保留预先运行的驱动；只有自行启动且最后租约退出时才请求停止。
  • unknown/partial 与真实零值分别保留。

由 Launcher 选择 Light；实体身份核对与能力状态仍适用。

Windows 与精确偏移支持

collection-only 表示可采集身份，不代表已有完整偏移支持。报告接入先只读校验 valid=true，再进入正式矩阵。

20

MCP 设置与 GUI 连接

当前主线通过外部 stdio sidecar 与同机命名管道连接真实 Qt GUI，提供页面发现、控件树、表格切片、文本读取和原生控件动作；特殊控件按已登记的只读适配器开放。

  1. 确认下载的主程序构建支持 MCP，安装配套 sidecar 与 Python 依赖；旧发布包可能早于该功能。
  2. 在“设置 → MCP”启用本次服务。自动启动默认关闭，路径与启动偏好通过“应用/取消”保存；本次启停立即生效，两者分开。
  3. 客户端配置使用真实 Python、sidecar 与主程序完整路径。--ksword-exe 默认 --startup-policy fail；只有明确选择 auto 才在调用时启动。固定 PID 模式需指定实际 PID。
  4. 先读取 hello、pages 和 snapshot，再操作当前对象。按最新表格 revision 选行；销毁或重新创建的控件需重新获取对象 ID。
已注册、工具已发现、GUI 已连接与业务成功分别核对。

accepted / dispatched 只描述控件调用。后台任务、确认弹窗与结果仍须从原页面回读；动作、字段修改和选行要求明确确认，保留原业务确认流程。

  • 普通复选框用布尔 true/false 指定状态；toggle 反转当前值。同值设置不反向切换，表格单元格勾选需要相应模型能力。
  • 连接校验用户、会话及完整性级别；UAC 启动例外仅绑定本次客户端真实 PID 与创建时间。没有 TCP 服务，不自动重启已有实例或重试业务请求。
  • 设置操作日志保留最近 1000 条内存记录，记录方法和回执，不记录参数或读取结果；退出程序后不保留。

MCP 的 CLI/IOCTL 工具可独立于 GUI 配置运行，按下一节单独核对权限与结果。

CLI 与原始 IOCTL

CLI 已接入 Light R3 的 66 项迁移清单，包含进程、文件、注册表、服务、网络、监控、对象命名空间和安全证据。R3 查询是否需要管理员由具体命令决定；R0 命令通常需要已加载的配套驱动。

KswordCLI.exe help
KswordCLI.exe help process
KswordCLI.exe help system ioctl call

--json 保留 backend、success/partial/unsupported/failed、data 与 diagnostics。保留实际退出码，不能把空结果或 partial 当作完整成功；纯 R3 命令默认 R3，不自动切换到 R0。

system ioctl decode 只解析编码，不发送请求。system ioctl call 经既有 ArkDriverClient 向固定 KSword 控制设备发送一次有界请求，全部要求 --confirm，输入与输出各上限 1 MiB。编码和缓冲区 ABI 来自配套 shared/driver/；传输成功不能替代响应中的业务状态。不会自动装驱动、提权或重发。

MCP 先用 ksword_cli_status 核对路径，再用 ksword_cli_help 读取原生帮助。任意命令和原始 IOCTL 都要求 confirmed=true，原生命令所需的 --confirm 仍需提供。超时可能留下未知业务结果，先回读状态再决定下一步。

复杂报告与权限工作台

进程详情 → Process Detail Evidence → 结构报告保留分区、类型和字段层级。搜索包含折叠后代及完整原始值；分区复制、复制全部和导出基于同一规范文档，不按当前折叠或筛选截断。生产者未载入或已截断的目录项仍保持原限制。

权限工作台包括账号、组成员、直接 LSA 权利分配、令牌对比、访问诊断、登录会话、身份启动和手动快照。操作前确认 SID、进程创建时间与实际令牌，修改后核对回读。

  • 直接 LSA 分配不等于当前进程的有效令牌；策略修改不会立即重写已有令牌。
  • AccessCheck 是指定令牌、描述符与掩码的诊断证据，不保证真实文件、注册表或服务操作一定成功。
  • 不可读、缺失与相等分别处理；手动快照不是所有对象在同一时刻的原子系统快照。

CKS 免重置研究

CKS 的第三个子页“免重置研究”区分两条候选：启动前重新建立登记，以及可能触及登记的保留应用修复安装。它们都未验证成功，不是受支持的免重置启用流程。

既有关闭登记、启动许可、PK/KEK 信任与基础策略签名分别影响准入。Licensed=1、策略已部署或普通刷新成功不能证明 CKS 已生效；判断需要实际 CKS 状态、目标驱动加载、CI 事件及重启/更新后的持续性证据。
